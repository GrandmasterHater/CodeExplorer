Описание агента:

Назначение - помощь в изучении проекта и его кодовой базы, ответы на вопросы с минимальной затратой токенов. 

Принцип работы:

1. Получаем из кодовой базы направленный граф где узлы это единицы кодовой базы - классы, функции, директории. 
2. На основе графа и исходного кода строим семантическую модель.
3. Описание векторизуется и хранится в векторной БД. Связь поисковой записи с узлом графа необязательна. При сопоставлении используются исходный файл и сведения о символе: имя, содержащий класс и сигнатура, где применимо. Неоднозначные совпадения не считаются установленной связью.
4. Единицы семантического поиска — файл и функция/метод с контекстом файла и содержащего класса, если он есть. Для файла формируется описание его общей роли, для функции — описание её текущего поведения и места в этой роли. Каждая запись связана с исходным файлом и, для функции, с конкретным символом.
5. Файл является единицей обработки и обновления индекса. Один файл может порождать несколько поисковых записей. При ответе агент может объединять найденные записи и уточнять их по исходному коду и графу связей.
6. Основная индексация обрабатывает только поддерживаемые кодовые файлы.
7. Отдельный поиск конфигураций обнаруживает кандидатов по именам, расширениям и расположению, без генерации смысловых описаний. Пользователь выбирает, какие файлы разрешить анализировать и добавить в библиотеку. Для выбранных файлов создаются описания и поисковые представления.

Инструментарий: 

- codegraph - для построения графа кодовой базы.
- Qdrant - Dense vector + Sparse vector + RRF
- Pydantic AI - фреймворк для создания агента с набором инструментов.

Общая структура:

1. Выделяем провайдер для работы с codegraph. Его функции:
   - Получить количество нод.
   - Сделать запрос к codegraph. Передаётся строка запроса.
2. Выделяем провайдер для работы с семантической БД. Его функции:
   - Проверить наличие семантической бд.
   - Создать семантическую бд.
   - Добавить запись о не кодовом файле, это может быть конфиг или мета-информация объекта.
   - Добавить запись о файле с кодом.
   - Добавить запись о функции. В таком случае передаётся как описание файла, так и описание функции, чтобы функция содержала контекст файла.
   - Поиск по запросу. Передаётся строка запроса.
3. Добавляем функцию, которая формирует семантическую бибилиотеку проекта. Её задача зафиксировать смысл который несёт текущая реализация конкретной функции, файла с кодом или конфигурационного файла. В качестве точки старта указываем нужную директорию для анализа. Функция проходит рекурсивно по файловой системе и анализирует файлы.
5. Создаём агента, который в зависимости от запроса для сбора информации использует либо граф, либо векторную бд либо всё вместе. И формирует итоговый ответ.
Если запрос содержит вопрос в стиле "Где реализована авторизация?" или "Что отвечает за обработку шага боевой логики игрового поля?", то сначала по семантическому поиску и поиску совпадения слов (в семантической бд храним не только вектор но и исходное описание) находим те файлы которые за это отвечают. При необходимости детального описания выполняется дополнительный запрос к codegraph для получения детальной информации о связях и дополнительных сущностях. Глубина поиска и защита от зацикливания будут подбираться итеративно. Выявляем связи, выполняем по ним семантический поиск. Если связи не относятся к вопросу то поиск останавливается и имеющиеся данные отдаются LLM для формулировки ответа.


Итерация 1 - ожидаемый результат:

Агент запускается, может вызываться из IDE, и отвечает на вопросы по кодовой базе.

Примеры вопросов для которых задействуется агент:
- Где определён `PaymentService`? 
- Кто вызывает `validate_order`?
- Какие зависимости у "ChatService"?
- "Где реализована авторизация?"
- "Что отвечает за обработку шага боевой логики игрового поля?"

На данном этапе качество ответов на вопросы должно быть не хуже прямых запросов к LLM по кодовой базе.

Главная ценность - получен опыт написания собственного агента через Pydantic AI.

Итерация 2 - ожидаемый результат:
- Тюнинг агента. В зависимости от результатов итерации 1 находим слабые места или места которые явно можно улучшить. Прежде всего делаем упор на качество поиска и способность из смысла строить представление о текущей реализованной архитектуре кодовой базы. На этом этапе может быть принято решение о дополнительных итерациях.
